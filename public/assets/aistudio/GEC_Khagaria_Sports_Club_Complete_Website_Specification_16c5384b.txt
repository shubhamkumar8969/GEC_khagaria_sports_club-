1. Project Overview

Create a modern, responsive, secure, Firebase-connected website for the Sports Club of Government Engineering College, Khagaria. The website must support multiple independent events. Each event can contain multiple games. Each game can accept individual or team registrations, use its own registration form fields, and have its own participant list and status workflow.

The central requirement is one admin system that controls all events, games, registrations, participants, announcements and downloadable reports. For example, an administrator creates the event UMANG'27, adds Cricket, Volleyball, Kabaddi, Football, Badminton, Chess and other games, opens registration, reviews entries and exports filtered participant records.

1.1 Main Goals

Publish a professional public website for the Sports Club.

Allow admins to create, edit, publish, close, archive and manage multiple events.

Allow each event to contain any number of games.

Support individual, doubles and team-based registrations.

Generate registration forms based on the selected game and its configured fields.

Maintain a central participant database with event-wise and game-wise status.

Search, filter, select and export all or selected participant records.

Provide secure admin access with different permission levels.

Work reliably on mobile phones, tablets and desktop computers.

Keep the website maintainable so future sports events can be added without rebuilding it.

1.2 Success Criteria

An authorized admin can create an event and add games without developer assistance.

A student can find an open event, choose a game and submit a valid registration.

An admin can find a registration using name, registration number, phone or email.

An admin can filter by event, game, branch, year, status and date range.

An admin can export all filtered rows or only manually selected rows to Excel/CSV.

A participant's status is tracked separately for each game registration.

Unauthorized users cannot access private participant data or admin functions.

The website is usable on common Android mobile browsers and desktop browsers.

7.1 Common Registration Fields

7.2 Registration Workflow

Student opens the Events page.

Student selects a published event.

Student selects an open game.

Website checks that registration is open and capacity/deadline has not been reached.

Website displays the correct individual/doubles/team form and custom questions.

Student enters details and accepts the registration declaration/privacy notice.

A unique registration record is created and a non-guessable reference is returned.

Student sees a confirmation page and, if enabled, receives a confirmation email.

Admin sees the new registration in the dashboard and can review it.

7.3 Duplicate Registration Protection

Define duplicate rules with the Sports Club: normally one active registration per participant per event/game.

Use a deterministic or transaction-checked uniqueness key based on normalized participant identity + eventId + gameId.

Do not rely only on frontend checks; enforce duplicate prevention through a trusted backend transaction or callable function.

Allow an authorised admin to resolve genuine duplicate cases with an audit record.

For team entries, prevent duplicate team submissions where the same captain/team key is used.

7.4 Team Registration

Captain submits the team registration and provides team name and member details.

Team size must follow the game's configured minimum and maximum.

Each member should include the agreed identity fields such as name, enrollment number, branch and year.

The system should check duplicate member enrollment numbers within the same team and, where policy requires, across teams for the same game.

Optionally allow a captain to invite members to confirm participation; this can be a later enhancement.

Admin can view the team as one entry and inspect its member list.

10. Excel, CSV and Reports

10.1 Export Requirements

Export must use the exact active filters and selected rows. The UI must clearly state whether it is exporting selected records, the current page, or all records matching filters.

10.2 Excel Workbook Structure

Sheet 1 — Registrations: one row per registration, with event, game, participant/captain, branch, year, status and timestamps.

Sheet 2 — Team Members: one row per team member, linked by registration ID.

Sheet 3 — Summary: counts by event, game, branch and status.

Sheet 4 — Custom Answers (optional): registration ID, field label and answer, or flatten selected fields into the main sheet.

10.3 Export Safety

Exports must be generated only after server-side authorisation.

Do not expose unrestricted Firestore queries or download URLs to public visitors.

Escape spreadsheet formula-leading characters in untrusted text values to reduce CSV/Excel formula injection risk.

Use stable column headings and consistent date/time formatting.

Use pagination/batched fetching for large exports.

Record export actions in the audit log, including admin, filters and timestamp.

Do not include private fields unless the admin role is permitted to export them.

11.3 Data Modelling Notes

Use generated document IDs. Keep eventId and gameId references in registration documents.

Store game documents as subcollections under their event to preserve the event/game hierarchy.

Keep registrations in a top-level collection for efficient global participant search and exports.

Use server timestamps for createdAt/updatedAt and status history.

Use denormalised eventName and gameName snapshots in registration documents if needed for reliable historical exports after a game is renamed.

Do not store large image files in Firestore; store them in Firebase Storage and keep the storage path in Firestore.

Define Firestore indexes for the filter combinations actually used by the dashboard.

Avoid storing unnecessary sensitive data. Establish a retention and deletion policy with the college.

12. Security, Privacy and Access Control

Security is a core requirement, not a final polish task. Participant details such as phone numbers, email addresses and enrollment numbers are private student information.

12.1 Authentication

Only invited/approved administrators can access the admin dashboard.

Do not provide public admin self-registration.

Create admin accounts through a trusted super-admin workflow or Firebase Admin SDK in a secure environment.

Use Firebase Authentication email/password or an institution-approved sign-in provider.

Enable password reset and account deactivation.

Use custom claims or a trusted admin-role document, with rules that prevent users from assigning themselves elevated roles.

Require re-authentication for sensitive actions where appropriate.

12.2 Firestore and Storage Rules

Write and test restrictive Firestore and Storage Security Rules before launch. Public users should only read published public event/game fields. Public registration creation should be limited to valid registration submissions, ideally through a callable Cloud Function that validates the payload. Public users must not read the global registrations collection. Only authorised admins may read participant records, and event admins must be restricted to assigned events.

// Conceptual policy only — not production-ready rules.
// Implement and test complete rules in Firebase Emulator Suite.

Public:
  read published event and game information only
  cannot read registrations, admin records or audit logs
  cannot create/update events, games, admin roles or statuses

Student:
  may submit a valid registration through a trusted endpoint
  may read only their own registration through a verified ownership flow
  cannot change approval status or admin-only fields

Event admin:
  may read/manage registrations for assigned event IDs
  may update only permitted registration/status fields
  cannot grant themselves roles or edit global security settings

Super admin:
  full authorised management access
  all privileged changes are audit logged

12.3 Privacy Requirements

Display a short privacy notice before registration explaining why information is collected and who can access it.

Collect only data needed for event administration.

Do not publicly display phone numbers, email addresses or enrollment numbers.

Use secure, non-guessable registration references; do not expose sequential IDs as access credentials.

If students can check their own registration, verify identity through an appropriate secure method such as authenticated login or one-time verification.

Define how long registrations are retained and who can request correction/deletion.

Do not upload identity documents or sensitive records unless the institution requires them and access controls are in place.

12.4 Audit Logging

Log event creation, editing, publication, closure and deletion/archive.

Log game creation/editing and registration form changes.

Log approval, rejection, waitlisting and other status changes.

Log exports, bulk actions, admin invitations, role changes and account deactivation.

Audit entries should be append-only for ordinary admins and readable only by authorised roles.

13. Notifications and Communication

Show an on-screen success message after registration.

Optionally send registration confirmation email using a trusted email service or Cloud Function.

Optionally send approval/rejection/waitlist emails with safe, editable templates.

Display published announcements on the public website.

Do not promise SMS/WhatsApp notifications unless a provider and budget are approved.

Provide notification settings and test mode for admins before sending messages to real participants.

14. Validation and Business Rules

15. Search, Pagination and Performance

Use server-side filtering and pagination for large registration collections.

Default page size may be 25 or 50, with options such as 25/50/100.

Debounce text search and avoid fetching the full database for each keystroke.

Create Firestore composite indexes for supported combinations of eventId, gameId, status, branch, year and createdAt.

Show loading skeletons, empty states and clear error messages.

Use image compression/responsive images for event banners.

Lazy-load non-critical routes and images.

Avoid unnecessary real-time listeners on large participant lists; use one-time paginated queries unless live updates are genuinely needed.

23. Final Product Definition
